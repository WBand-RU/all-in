# План реализации WBand MVP

Дата: 22.10.2026. Статус: реализация идёт; T01–T10 и T06a проверены, далее T11.
Требования: [MVP_REQUIREMENTS.md](../docs/MVP_REQUIREMENTS.md).
Задачи и зависимости: [todo.md](todo.md).

## 1. Исходная точка

Оценка ниже основана на чтении текущего кода, а не на новом прогоне тестов.
Индекс graphify использован для навигации; выводы сверены с исходниками.

| Требование | Уже есть | Необходимо довести |
| --- | --- | --- |
| MVP-01 | BFF/Keycloak, группы, членство, приглашения | Четыре роли вместо Owner/Admin/Member, передача владения, согласованные права, собственный модуль групп |
| MVP-02 | CRUD песен, поиск, EF Core, матрица содержимого | Размер, теги, поиск по партиям, AND-фильтр, свойства частей, собственный модуль репертуара |
| MVP-03 | Plain text, сохранение партии/ячейки, подсветка скобок | Проверить весь цикл сохранения и связать его с полными версиями; адаптивность и RU/EN новых экранов |
| MVP-04 | Примеры JSON и утилита экспорта | Пользовательский импорт, предпросмотр, повторный импорт, атомарность песни и отчёт |
| MVP-05 | Отдельный EventModule, EF-схема events, CRUD | Позиции вместо Guid[] SongIds, повторения, тональность/структура позиции, текстовые пункты и подсказки, корзина, защита ссылок |
| MVP-06 | Просмотр сцены, выбор партии по пользователю/песне | Транспонирование, каподастр, позиции программы и ручное обновление снимка |
| MVP-07 | Проверка BFF-сессии, локальное предпочтение партии | Оффлайн-оболочка, локальные пакеты события, атомарное обновление, изоляция аккаунтов и очистка вкладок |
| MVP-08 | SongRevision и восстановление метаданных | Полные снимки содержимого, версии всех изменений, предпросмотр, удаление/возврат версии |
| MVP-09 | Мягкое удаление/восстановление песни | Общие права корзины, события и версии, очистка через 30 дней, целостность ссылок |

Известные риски прошлой проверки: непостоянные обрывы PostgreSQL-потока
и результаты 75–77/77 серверных тестов; API Dockerfile использует прежние пути;
App/web/Dockerfile отсутствует; часть тестовых проектов не входит в решение.
Их актуальность перепроверяется в первом этапе, а не предполагается доказанной.
Пользовательское изменение App/WBand.AppHost/WBand.AppHost.csproj не трогать
без сопоставления с целью конкретной задачи.

## 2. Архитектурные решения

- Один ASP.NET Core host, одна PostgreSQL; EF Core, без Marten.
- Группы/профили: `Modules/WBand.Modules.BandModule`, схема `bands`.
  Репертуар: `Modules/WBand.Modules.SongModule`, схема `songs`.
  События: существующий `Modules/WBand.Modules.EventModule`, схема `events`.
- Каждый модуль владеет своим DbContext, миграциями и контрактами. Не подключать
  прежние Marten-модули. Сохранять данные и идентификаторы при переносе из public.
- Зависимости: SongModule использует контракты BandModule; EventModule —
  контракты BandModule/SongModule. Обратные зависимости между модулями запрещены.
- Межмодульные операции координирует application-слой хоста через Wolverine.
  Проверки ссылок на события не добавляются как зависимость SongModule → EventModule.
- Для удаления песни/частей, применения версии, повторного импорта и записи
  программы нужен единый протокол конкурентного доступа: транзакция PostgreSQL,
  общий DbConnection/DbTransaction участвующих EF-контекстов и согласованный
  порядок блокировок. Предложение: сериализация таких изменений по группе;
  чтение ссылок выполняется публичным контрактом владельца данных.
  Только предварительная проверка вне транзакции недостаточна.
- Позиция программы имеет собственный ID. Две позиции одной песни независимы;
  ссылки на части хранят их стабильные ID, а не имена. События в корзине сохраняют ссылки.
- Полная версия песни захватывает метаданные, части, партии и ячейки в одной
  транзакции изменения. Для прежних metadata-only версий нельзя выдумывать
  утраченное содержимое: отдельная миграционная политика и явный признак неполноты.
- Outbox/inbox — только для выявленных обязательных асинхронных действий.
  Аудит существующих RabbitMQ-публикаций: убрать ненужные либо обеспечить
  атомарную доставку обязательных. Не маскировать сбои повторами всех HTTP-команд.
- Оффлайн — браузерная возможность без требования установки PWA. Локальные
  пакеты привязаны к аккаунту; токены OAuth не сохраняются в пакете.
  Скачивание в staging, переключение активной копии только после проверки полноты.
  Серверные операции продолжают проверять действующую BFF-сессию.

## 3. Последовательность

1. **Основа:** воспроизведение нестабильности, запуск Aspire, BFF-тесты, CI/упаковка.
2. **Границы модулей:** перенос групп и репертуара небольшими семействами данных
   и обработчиков, с проверкой прежних HTTP-сценариев после каждого переноса.
3. **Группы и репертуар:** права/владение, поля/поиск, структура и полный редактор.
4. **События и целостность:** позиции, повторения, текстовые пункты, настройки
   структуры/тональности, конкурентные проверки ссылок и корзина событий.
5. **Версии/корзина:** полные снимки, предпросмотр, применение, удаление и очистка.
6. **Импорт:** чистое преобразование JSON → предпросмотр → атомарное применение.
7. **Сцена:** музыкальные преобразования, настройки пользователя, стабильный снимок.
8. **Оффлайн:** пакет события, локальная оболочка, ручные обновления и очистка аккаунта.
9. **Приёмка:** сквозные роли, браузеры, экраны, нагрузка и восстановление из резервной копии.

Срезы доводятся до API/UI/проверки; горизонтальный перенос модулей ограничен
этапом 2 и не превращается в переписывание работающего приложения. Каждый
дальнейший срез оставляет доступным ранее проверенный сценарий.

## 4. Предлагаемые технические параметры приёмки

Это предложения для проверки плана, а не дополнительные уже согласованные требования.

### JSON

- `content.name` → название; `artist` → автор/исполнитель; `key` → тональность;
  `tempo` → BPM; `signature` → размер; `tags` → теги.
- Отсутствующие необязательные поля не заполнять фиктивными значениями.
  Нераспознаваемые значения показывать в предпросмотре для исправления.
- `id`/`bandId` источника не дают доступ к группе назначения; назначение выбирает
  пользователь, права проверяет сервер. Исходный ID хранится отдельно от нового ID WBand.
- Остальные поля (например, description, releaseDate, number) показывать как
  несопоставленные с предупреждением, не добавляя скрытые доменные поля.
  До подтверждения результат и исходные текстовые источники доступны для сверки.
- Нужен отдельный тестовый случай повторного импорта в песню в корзине:
  предупреждение, отсутствие автоматического восстановления или новой копии.
- При обновлении сохранять ID сопоставленных частей, используемых событиями;
  несовпадения требуют ручного разрешения. Сравнение только по имени запрещено.

### Экраны и браузеры

- Контрольные viewport: 360×800, 768×1024, 1440×900 CSS px; портрет/альбомный
  режим сцены. Управление не обрезается, текст не перекрывает кнопки.
- Chromium/Firefox/WebKit automation плюс реальная проверка Chrome Android
  и Safari iOS на доступных устройствах. Эмуляция WebKit не считается полной проверкой iPhone.
- Для версии браузера/ОС фиксировать точную сборку в отчёте приёмки.
- Если браузер запретил хранение, исчерпана квота либо локальная копия очищена,
  приложение сообщает об отсутствии готового пакета; старый рабочий пакет
  не уничтожается неудачным обновлением.

### Нагрузка и 2 секунды

- Обязательные ориентиры: 100 пользователей одновременно, 1 000 песен на группу,
  событие из 100 позиций. Они не становятся ограничениями регистрации/библиотеки.
- Предложение для воспроизводимой фикстуры: две группы по 1 000 песен,
  на песню 20 частей × 3 партии, до 1 КиБ текста на ячейку; новые данные
  синтетические, реальные 277 JSON отдельно проверяют совместимость импорта.
- 100 независимых сессий: просмотр песен/событий, поиск/теги, сохранение правок;
  разные объекты для обычных правок, конфликтующие запросы отдельным тестом.
- Окружение, оборудование и сеть записываются в отчёт; предложение контрольного
  стенда: 4 vCPU, 8 ГБ RAM, SSD, сеть клиента RTT до 50 мс.
- Две секунды измерять от действия до отображения результата в браузере.
  Показывать max/p95/p99 и ошибки; p95 не заменяет согласованный предел 2 с.
  Измерительное окно: 2 минуты прогрева и 10 минут нагрузки. Исключённые
  импорт/скачивание измеряются отдельно с проверкой прогресса и атомарности.

## 5. Definition of Done

- Пройдены критерии соответствующего MVP-ID, положительный сценарий и запреты
  на уровне API; проверены конфликты/повторы там, где меняется целостность.
- Миграции проверены на пустой БД и копии прежней схемы без потери данных;
  перед эксплуатационной миграцией есть резервная копия и план восстановления.
- Нет незаявленного изменения HTTP-контракта. После изменения HTTP генерируются
  клиенты из OpenAPI; сгенерированные файлы не редактируются вручную.
- Применимые unit/integration/browser-тесты, lint/typecheck/build проходят.
  Прежние падения не исключаются из набора ради зелёного результата.
- UI сохраняет Base UI/base-nova; новые строки RU/EN, управление клавиатурой,
  проверка узкого экрана. Скриншот сохраняется для заметного изменения UI.
- Проверены границы модулей и отсутствие новых Marten/legacy-зависимостей.
- Одна задача — один проверенный Conventional Commit; не включать чужие правки.
  При ограничениях среды точно указывать непроверенное, не объявляя срез готовым.

## 6. Проверки

Из корня: `dotnet build WBand.slnx --configuration Release`,
`dotnet test WBand.slnx --configuration Release`,
`python3 .github/scripts/test-detect-affected.py`.
Из App/web: `bun run lint`, `bun run typecheck`, `bun run test`, `bun run build`.
Генерация только после изменения HTTP: `bun run generate-api-clients`.
Запуск через `aspire start --non-interactive --apphost App/WBand.AppHost/WBand.AppHost.csproj`.
Конкретные новые команды browser/load-тестов фиксируются в задачах их подключения.
Рабочий Webpack-build при проблемах Turbopack фиксируется как отдельная проверка,
а не как доказательство прохождения стандартного build.
