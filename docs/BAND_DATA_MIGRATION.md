# Владение данными групп

BandModule владеет пятью таблицами в схеме `bands`: `users`, `bands`,
`band_members`, `band_departures`, `band_invitations`. EF-модель хоста содержит
только песни. Межмодульные связи представлены скалярными ID; физические внешние
ключи PostgreSQL сохранены и после переноса ссылаются на `bands.users`/`bands.bands`.

## Порядок обновления

1. Остановить старый API: прежний процесс продолжает обращаться к `public`.
2. Сохранить полный custom-format `pg_dump` и проверить восстановление в отдельной
   БД. Backup содержит пользовательские данные; хранить вне git с правами 0600.
3. Запустить новый API. `DatabaseSetup.ApplyMigrations` сначала применяет миграции
   хоста, затем `BandModule.ApplyMigrationsAsync`.
4. Проверить `/health/ready`, вход, список групп и работу песен/событий.

`ReleaseBandOwnership` удаляет сущности групп из snapshot хоста, **без DDL**.
Исторические миграции хоста остаются неизменными и создают прежнюю структуру
при развёртывании монолита с нуля.

`InitialBands` выполняется одной транзакцией:

- Если все пять таблиц находятся в `public`, переносит их через `ALTER TABLE SET SCHEMA`.
  ID, данные, OID таблиц/индексов/ограничений и входящие FK не пересоздаются.
- Если таблиц нет в обеих схемах, создаёт хранилище модуля.
- При неполном наборе `public` или уже существующих целевых таблицах отказывает.
  Нельзя автоматически объединять две потенциально разные копии данных.

История модуля хранится в `bands.__band_migrations`. Повторный запуск EF-миграций
ничего не переносит повторно. При ошибке на середине DDL транзакция возвращает
все таблицы в прежнее состояние; это проверено конфликтом имени индекса.

Нельзя вызывать `EnsureCreated` вместо миграций или удалять историю для повторного
принятия таблиц. Передача владения не означает удаление физических FK.

## Откат

Остановить API перед откатом. Сначала откатить миграции **BandDataContext** до `0`,
затем при необходимости откатывать миграции хоста. `InitialBands.Down` возвращает
все пять таблиц в `public` без удаления данных, в том числе созданных после
развёртывания с нуля. Схема и таблица истории модуля могут остаться пустыми.

Если в `public` уже существует любая из целевых таблиц, откат отказывает до
первого переноса. Сначала выяснить происхождение конфликтующей таблицы; миграция
не перезаписывает её. После отката можно повторно применить `InitialBands`.
При аварийном восстановлении использовать проверенный полный backup.

## Проверка T08–T10

`BandMigrationTests` проверяет наполненную прежнюю схему, пустую БД,
повторный запуск, перенос/откат с сохранением содержимого и OID, частичную/
конфликтующую схему, ошибку посередине DDL и конфликт отката. В исходных данных
есть история выхода и все пять статусов приглашений с временными полями.
`DatabaseSchemaTests` проверяет расположение таблиц, отдельные истории миграций
и все 14 пользовательских FK к Keycloak subject с `ON DELETE RESTRICT`.
Прежние HTTP-тесты проверяют TTL/отзыв/конкурентное принятие приглашений,
единственность членства, права и атомарное создание группы с владельцем.

Проверка локального backup: SHA-256
`009e4b3feaf55e8fbdbe0507f7e104e7ee8a5bec78f9943973efe7b353063c4e`;
восстановление в отдельную БД, два запуска миграций и сверка данных/OID.
Отдельно сверены все десять таблиц до/после миграции рабочей локальной БД.
Полный Release-набор — 122 теста; контейнерный сценарий BFF/API — создание
группы, песни и события, последующее чтение события с ответом 200.
